# LARVIVA Interactive Hatchery Journey — prototype

A self-contained, responsive module for the LARVIVA landing page. Visitors switch between the **Fish** and **Shrimp** portfolios. They can then explore the development stages and see which LARVIVA product families are relevant to each stage. Selecting a product opens its details.

The module is for product discovery and education. It does not give feeding recommendations. The panel always shows a reminder that product selection depends on more than developmental stage.

> **Content status.** Product facts come from the project brief and the supplied LARVIVA range sheets. All particle sizes are flagged `verified: false`. They show a "Provisional" badge and must be checked against approved technical documentation before publication. Stage descriptions are draft copy for marketing/technical approval. No product URLs are set, so no "View product details" links appear yet.

## Run it

Open `index.html` in a browser. It needs no server, no build step and no dependencies.

```bash
npm run build   # re-pre-render index.html + export data/*.json after editing data
```

```bash
npm test        # Playwright smoke test (desktop, keyboard, mobile, no-JS)
```

## How it behaves

- **On load**, Fish is selected and the whole journey (First feeding → Co-feeding / Weaning → Post-weaning → Nursery) is shown. Product bars sit beneath the stages they cover, and an instruction line says that everything is interactive.
- **Broodstock nutrition and Live-feed enrichment** are shown as *connected hatchery activities* in a separate dashed band, labelled as not being developmental stages. LARVIVA Broodstock and MultiGain sit there.
- **Selecting a stage** highlights it. Its related products are outlined, and unrelated products are dimmed but stay visible. The panel shows the stage description and its related products. Selecting the stage again clears the selection.
- **Selecting a product** shows its details: name, feed type, relevant stages, application, diets, particle size and any notes. The stages it covers are marked "Relevant". Empty fields are never displayed.
- **Switching Fish/Shrimp** swaps the journey and resets the selection without reloading. The layout stays the same.
- **Particle-size chart**: Shrimp shows each product's µm range on a shared scale, and Fish shows grade sizes. The shrimp product cards and the detail panel also show the range.
- **Responsive**:
  - **Desktop (≥ 1024 px):** chevron journey with a sticky side panel.
  - **Tablet:** the panel moves beneath the journey.
  - **Mobile (< 760 px):** the stages become a horizontally scrollable strip of cards, and the products become full-width tappable cards that list their stages. The panel sits below, and the page scrolls to it when a product is chosen. The page itself never scrolls sideways.

### Accessibility
- **Controls:** the Fish/Shrimp switch follows the WAI-ARIA tabs pattern (arrow keys, Home and End). Stages and products are `<button aria-pressed>`, and a product link is a real `<a>`.
- **Screen readers:** a polite live region announces changes. When a product is chosen from inside the panel, focus moves to the panel heading. Product bars include their stage names as text, so coverage isn't conveyed by position alone.
- **Visual cues:** colour is never the only cue. Products carry their names and feed types, and selected and related stages carry "Selected" and "Relevant" labels.
- **Focus, motion and contrast:** focus states are visible. `prefers-reduced-motion` and forced-colours mode are respected. Dimmed text keeps AA contrast.
- **Headings:** the module starts at `h2` and never adds an `h1`. Nothing is available only on hover.

### SEO
`npm run build` writes a static version of the module into `index.html` between the `LARVIVA:START/END` markers. That version contains both portfolios, all stage labels and every product's details as plain HTML. Crawlers and no-JS visitors get that content, and the script replaces it with the interactive version on load.

## Editing content

All of the following is done in the dataset (or the CMS). None of it needs code changes:

- **Rename or describe a product:** edit `name`, `description`, `application` or `productType`.
- **Add a product:** add an object to `products` with a new `id`. To give it a new colour, add a `--lj-family-<token>` value in the CSS and set `colorToken`. Unknown tokens fall back to a neutral colour.
- **Remove or hide a product:** delete it, or set `"published": false`. LARVIVA ZM is already in the data, unpublished and with no stage mapping, ready to be filled in.
- **Change stage associations:** edit `stages` (ids of stages and/or activities). A product can cover several stages. A published product with no mapping is listed under "Other products".
- **Particle sizes:** set `particleSize` (`range`, `grades` or `text`). Set `"verified": true` once the value is confirmed. Set `settings.showUnverifiedSpecs` to `false` for production so that unverified values are hidden.
- **Product URL:** set `url`. The "View product details" link appears only when it is set.
- **Markets:** `markets: ["VN"]` restricts a product to the pages whose module has `data-market="VN"`. `null` means all markets. `marketAvailability` is optional text shown to visitors.
- **Add a stage:** add it to the portfolio's `stages` array. The grid adapts to any number of stages.
- **Translations:** copy `larviva-journey.en.js` to e.g. `larviva-journey.es.js` and translate the text values, keeping every `id`. All interface strings are in `ui`. Load the locale file, or point `data-src` at the localised endpoint.

## CMS integration notes

The production version needs adapting to BioMar's CMS and frontend stack. Suggested approach:

1. **Model the content as collections.** The dataset maps directly onto three content types:
   - *Portfolio*: id, label, title, intro, size-chart settings, an ordered list of *Stages*, and an ordered list of *Activities*.
   - *Stage/Activity*: id, label, description, illustration asset.
   - *LARVIVA Product*: the fields listed at the top of the dataset. *Stages* is a multi-reference, *Markets* a multi-select of the site's markets, and *url* a link to the existing product page.

   Translations use the CMS's normal localisation. Interface strings (`ui`) become a dictionary or a singleton "module settings" entry.
2. **Expose the data as JSON** in the exact shape of `data/larviva-journey.en.json`: either an API route (`/api/larviva-journey?lang=en&market=VN`) or JSON embedded in the page by the template. Use it with `<section data-larviva-journey data-src="…" data-market="…">`.
3. **Server-render the markup.** `LarvivaJourney.renderModule(LarvivaJourney.prepare(data, {market}), {interactive: false, illustrations})` is a pure function and runs in Node, so a Node-based frontend (Next.js, Nuxt, Astro) can call it directly. Other stacks (.NET, PHP) can reproduce the static markup in a template. `scripts/build.js` shows the pattern.
4. **Ship the CSS and JS through the site's asset pipeline.** Map the CSS tokens to the BioMar design system's variables (font, navy, focus colour, radii). Everything is namespaced `.lj` / `lj-`, so it won't clash with site styles. The script has no dependencies and exposes `window.LarvivaJourney.init(element, {market, illustrations, onChange})`. The `onChange` callback can feed analytics.
5. **Replace the placeholder illustrations** with approved LARVIVA artwork as CMS media, referenced by the stage's illustration field.
6. **Before go-live:**
   - verify every particle size and set `verified: true`
   - set `showUnverifiedSpecs: false`
   - add the approved product URLs
   - get the stage descriptions approved
   - remove the prototype banner in `index.html`

## Not included (deliberately)

The range sheets also show **Inicio Plus M**, **Inicio Focus/Maxio**, **Balance**, **Prime Perform** and **LARVIVA ZM**. The brief did not specify their stage mappings or specifications, so nothing is invented for them. They can be added through the dataset once confirmed. LARVIVA ZM already has an unpublished placeholder entry.
